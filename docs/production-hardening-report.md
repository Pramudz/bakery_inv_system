## Authorization model

- Platform Administration manages global Modules, Identifier Types and administrative Sessions. Tenant users retain authenticated read-only catalogs. Direct tenant navigation to platform pages is blocked by `PlatformOnlyRoute`; backend guards are authoritative.
- Tenant Administrators retain tenant-specific Roles, User Roles and Role Permissions. Role/user ownership is checked by tenant in services. Eligible permissions must be active and belong to an enabled tenant module. The global permission catalog has no tenant mutation route.
- The normal login paths still issue hashed platform and tenant sessions. The new logout routes revoke the presented token. Explicit logout waits for the server request before routing away; if the request cannot be delivered, the browser clears local credentials but server revocation remains unconfirmed. Administrators can revoke tenant sessions through the platform screen.
- A guard request that began before concurrent revocation can finish. A subsequent protected request is denied. This is the normal boundary of request-level authentication.

Preflight requires no orphan invoice payments and no duplicate non-NULL collection key within a tenant. ## Master Drawer transaction map

`MASTER_REGISTER` is the implemented enum for the shared Master Drawer mode. A cashier batch ends only its cashier session; the shared register remains open. Independent approval records recipient and variance. Master count submission later freezes the register; independent verification closes it. Terminal register count uses the separate `TERMINAL_REGISTER` path.

Legend: **VERIFIED** means this audit ran actual MySQL against the authorized database for the named behavior; **CODE-SUPPORTED** means implementation and existing automated tests support it; **PARTIAL** means important runtime or network behavior remains untested. No physical cash handover or printer output can be made exactly once by a database transaction.

Checkout uses one TypeORM transaction for invoice, lines, payment, inventory balance/ledger and receipt state. Refund creation and stock restoration similarly share one transaction manager. Cashier batches and their coverage rows are saved with the session transition in one transaction. Master payout creates refund payment, cash movement and invoice recalculation in one transaction. These claims are source-supported unless the row above says VERIFIED.

Cash expected is opening balance plus attributed net cash tender minus change plus cash-in movements minus cash-out movements. Cashier batches omit the shared opening balance. Master closing compares system receipts/movements with approved, physically confirmed cashier contributions and direct master movements. Reversed cash receipts remain physically present until an explicit payout movement is recorded. Coverage rows and closing blockers prevent an attributed payment or cashier movement from being silently omitted from an approved close.
